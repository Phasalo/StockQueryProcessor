# Миграции PostgreSQL

Изменения схемы и начальных данных оформляются SQL-миграциями через `yandex-pgmigrate`. Версия инструмента задана в [pyproject.toml](../pyproject.toml), точные версии зависимостей — в [uv.lock](../uv.lock), конфигурация находится в [migrations.yml](../migrations.yml), SQL-файлы — в [migrations/](../migrations/).

Команды выполнять из корня проекта после `uv sync --locked`. База PostgreSQL должна существовать до запуска миграций. Подключение задаётся стандартными переменными PostgreSQL:

```sh
export PGHOST=localhost
export PGPORT=5432
export PGDATABASE=warehouse
export PGUSER=postgres
```

Пароль передать через `PGPASSWORD` или `.pgpass`. `pgmigrate` не читает `config.py` и `.env`; переменная приложения `POSTGRESQL_PASSWORD` сама по себе на него не влияет. Пустая строка `conn` в конфигурации позволяет драйверу использовать переменные PostgreSQL.

Посмотреть версии, проверить ожидающие миграции без сохранения и применить их:

```sh
uv run --locked pgmigrate -d . -t latest --check_serial_versions info
uv run --locked pgmigrate -d . -t latest --check_serial_versions -n migrate
uv run --locked pgmigrate -d . -t latest --check_serial_versions migrate
```

Складские таблицы находятся в `public`, записи исполнений — в `engine`. Конфигурация задаёт `search_path` равным `public`, а `schema: null` включает в pgmigrate режим нескольких схем с историей в `public.schema_version`. Объекты `engine` в SQL указываются с полным именем. Флаг `--check_serial_versions` запрещает пропуски номеров версий. В CLI версии 1.0.13 его нужно передавать явно: значение аргумента по умолчанию перекрывает булевую настройку YAML.

Для существующей БД без истории миграций сначала определить соответствие текущей схемы файлам проекта и подготовить переход. Команда `baseline` только отмечает версию; она не меняет таблицы и данные.

Историю хранит `public.schema_version`, служебный enum — `public.schema_version_type`. Собственная таблица версий не создаётся. Повторный `migrate` пропускает уже применённые версии и не перезаписывает справочники.

Создание объекта `Warehouse` не открывает соединение и не создаёт схему. Перед работой с БД миграции нужно применить явно.

Транзакциями миграций управляет `pgmigrate`: по умолчанию последовательные транзакционные миграции применяются одной транзакцией. Ошибка откатывает изменения этой группы вместе с записями версий. `BEGIN`, `COMMIT` и `ROLLBACK` для управления транзакцией в SQL-файлы не добавляются. `UnitOfWork` остаётся для операций приложения.

Правила добавления миграции:

1. Создать SQL-файл в формате `V<номер>__<описание>.sql` со следующим свободным целочисленным номером. Дубликаты и пропуски номеров не допускаются.
2. После применения файл не изменять и не переименовывать. Исправления и последующие изменения оформлять новой миграцией.
3. Для SQL с русскими строками добавить директиву `/* pgmigrate-encoding: utf-8 */`.
4. Проверить миграцию на временной PostgreSQL: применение, итоговую схему и данные, повторный запуск и откат при ошибке. Для изменения существующих таблиц также проверить сохранение старых данных.
5. Запускать миграции явно отдельной командой, а не при импорте библиотеки или создании репозитория.

Для тестов явно задать `TEST_DATABASE_DSN` с параметрами тестовой PostgreSQL:

```sh
uv run --locked python -m unittest discover -s tests -p test_migrations.py -v
```

Пользователю тестового подключения требуется право создавать базы. Каждый тест создаёт отдельную временную БД, запускает настоящий CLI `pgmigrate` и удаляет БД после проверки. Без `TEST_DATABASE_DSN` интеграционные тесты пропускаются.

[Официальное руководство PGmigrate](https://github.com/yandex/pgmigrate/blob/master/doc/tutorial.md).
